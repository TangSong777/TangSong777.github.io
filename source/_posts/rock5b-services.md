> 这篇不是教程，是一份「说明书」——记录这块板子到底承担了哪些工作，每项服务解决了什么问题，以及在什么场景下才真正派得上用场。

## 硬件

| 项目 | 规格 |
|---|---|
| 主板 | Radxa Rock 5B+ |
| SoC | RK3588（4×Cortex-A76 @1.8GHz + 4×Cortex-A55） |
| 内存 | 8 GB LPDDR5 |
| 存储 | 235 GB NVMe SSD（WD SN730） |
| 加速器 | Mali-G610 GPU + 6 TOPS NPU + 8K VPU |
| 网络 | 千兆有线 + WiFi 6 |
| 系统 | Debian 12 bookworm，kernel 6.1.84 |
| 常驻功耗 | 约 5–8 W |

放在宿舍角落，7×24 小时运行，接在宿舍路由器的有线口上。

## 一句话概括

这块板子目前扮演四个角色：**内容发布服务器**、**笔记流水线**、**远程串流客户端**、**个人网络中枢**。

## 逐项说明：解决什么问题，什么场景有效

### 一、博客与笔记发布

**问题**：想写点东西，但不想每次都手动整理、构建、上传。

**现在的方式**：

1. 在思源里写完笔记
2. 每天两次自动触发（04:15、13:00）
3. 脚本导出 → 过滤私密内容 → 转换成 Markdown → 构建 Hexo → 推送到 GitHub
4. GitHub Actions 自动部署

**真正有效的场景**：

- 平时在思源里随意记录，不用考虑格式
- 到点自动发布，完全不用管
- 私密内容（密码、他人隐私、草稿）自动排除，不会误发

**什么时候没效果**：

- 改版式、加新功能——还是要手动改主题配置
- 图片体积优化——需要单独跑脚本

### 二、服务器控制台

**问题**：想随时知道板子在干什么，不想每次都 SSH 上去敲命令。

**现在的方式**：浏览器打开 `server.yanghanlin.cn`，看到：

```
CPU 每核频率、温度、风扇转速
内存与交换分区
磁盘占用
网络各接口的 IP 与实时速率
服务状态（8 个 systemd 单元）
定时任务的触发时间与倒计时
串流状态（分辨率、码率、延迟、丢帧）
实时日志
网页终端
```

**真正有效的场景**：

- 串流卡顿时看一眼延迟和丢帧数据
- 排查服务异常时直接看日志
- 出门在外用手机确认板子还活着

**什么时候没效果**：

- 板子完全断网——那就只能用物理显示器
- 需要深挖历史趋势——面板只显示当前值，历史要看 SmokePing

### 三、远程串流

**问题**：想在宿舍用大屏玩笔记本上的游戏。

**现在的方式**：

1. 板子接显示器，跑 Moonlight 客户端
2. 笔记本跑 Sunshine 服务端
3. 通过 ZeroTier 虚拟网络连接
4. 板子负责硬件解码，笔记本负责编码

**实测数据**：

```
分辨率     1920×1080
帧率       60 fps
码率       8–10 Mbps
延迟       4–130 ms（直连时） / 200+ ms（走中继时）
帧到达率   95%–98%（网络正常时）
CPU 占用   约 13%（硬件解码）
```

**真正有效的场景**：

- 回合制、策略类游戏（对延迟不敏感）
- 看视频、浏览网页
- 笔记本性能足够时的远程桌面

**什么时候没效果**：

- 实时动作游戏——中继时延迟 200ms 会明显影响操作
- 网络不稳定时——每 1–2 分钟可能卡顿 2–5 秒
- 对画质要求高的场景——受码率限制

**已知限制**：宿舍网络在运营商 NAT 后面，ZeroTier 无法稳定打洞，会周期性回落到中继。这是物理网络的限制，不是配置问题。

### 四、岁月史书

**问题**：想把个人经历整理成结构化的时间线，但不想手动维护网页。

**现在的方式**：

1. 在思源里按固定格式记录事件（时间、地点、内容）
2. 发布流程自动提取数据
3. 生成静态站点，含总览、时间线、事件档案

**真正有效的场景**：

- 长期积累的个人记录
- 想按时间检索过去发生的事
- 分享给别人看的公开记录

**什么时候没效果**：

- 记录格式不规范——提取会失败或跳过低质量条目
- 需要复杂交互——纯静态页面，没有搜索和筛选

### 五、多站点统一管理

**问题**：四个站点分散在不同地方，各自有配置，容易混乱。

**现在的方式**：

```
博客       GitHub Pages（静态托管，快、免费、稳定）
岁月史书   板子本地 Node 静态服务
控制台     板子本地 Node 服务，带实时推送
管理中心   板子本地 Node 服务
```

通过 Cloudflare Tunnel 统一暴露，全部走 HTTPS，**板子不开放任何入站端口**。

**真正有效的场景**：

- 想加新站点时，只需要在板子上跑起来，加一条 Tunnel 路由
- 不想管证书——Cloudflare 自动处理
- 家里没有公网 IP 也能对外提供服务

**什么时候没效果**：

- 需要极低延迟——Tunnel 绕了一圈 Cloudflare，比直连慢
- 大文件传输——受 Tunnel 带宽限制

### 六、网络安全

**配置**：

```
SSH        只允许密钥登录，密码登录已关闭
fail2ban   连续 3 次失败封 2 小时
UFW        默认拒绝入站，只放行必要端口
业务端口    全部只监听 127.0.0.1
安全头     CSP、X-Frame-Options、HSTS、nosniff
```

**真正有效的场景**：

- 板子有公网 IPv6，会被扫描——fail2ban 自动挡住
- 服务只走 Tunnel，攻击面极小

**什么时候没效果**：

- 物理接触——谁都能拔电源
- 内部威胁——同局域网设备之间没有隔离

### 七、监控与告警

**当前状态**：

```
SmokePing   持续采集延迟数据，生成历史曲线
smartd      磁盘健康巡检
备份        每天自动打包关键数据
```

**缺口**：**没有主动告警**。磁盘满了、服务挂了、证书到期了——目前只能自己上去看。

这是下一步要补的。

## 网络架构

```
                    ┌─────────────────────────┐
                    │      Cloudflare          │
                    │  （Tunnel + 证书 + CDN）  │
                    └───────────┬─────────────┘
                                │ 出站长连接
                    ┌───────────▼─────────────┐
                    │     宿舍路由器            │
                    │  OpenWrt + ZeroTier      │
                    │  192.168.6.1             │
                    └───────────┬─────────────┘
                                │ 有线 千兆
                    ┌───────────▼─────────────┐
                    │      Rock 5B+            │
                    │  192.168.6.5             │
                    │  ├─ 4 个站点服务          │
                    │  ├─ 思源 / AdGuard       │
                    │  ├─ SmokePing            │
                    │  └─ Moonlight            │
                    │  ZeroTier 192.168.195.5  │
                    │  IPv6 240e:399:...       │
                    └───────────┬─────────────┘
                                │ ZeroTier
                    ┌───────────▼─────────────┐
                    │      笔记本              │
                    │  ZeroTier 192.168.195.2  │
                    │  Sunshine 服务端         │
                    └─────────────────────────┘
```

**三条通路**：

1. **公网 HTTPS** — 访客访问网站，走 Cloudflare
2. **ZeroTier** — 板子与笔记本互访，走虚拟局域网
3. **IPv6** — 从公网直接访问板子（需知道地址）

## 实际使用场景

### 场景一：在宿舍写笔记

```
打开思源 → 记录 → 关掉 → 第二天自动出现在博客上
```

不需要关心 Markdown 语法、图片路径、私密内容过滤。

### 场景二：在教室用平板看笔记

```
平板浏览器 → 打开博客 → 学习笔记栏目
```

内容来自前一晚的自动发布。

### 场景三：出门在外查板子状态

```
手机浏览器 → server.yanghanlin.cn → 看温度、服务、串流
```

不需要 SSH，不需要装 App。

### 场景四：宿舍大屏玩游戏

```
板子接显示器 → 双击 Moonlight 图标 → 连上笔记本
```

回合制游戏体验接近本地，动作游戏受网络限制。

### 场景五：排查网络问题

```
打开 SmokePing → 看延迟曲线 → 对照串流日志的时间点
```

能看出"卡顿时网络发生了什么"。

## 哪些做得好，哪些还欠着

### 做得好的

- 笔记到博客全自动，零干预
- 四个站点统一入口，访客体验一致
- 串流能用，且知道卡在哪里
- 有备份、有监控、有安全加固
- 所有服务都能在浏览器里看状态

### 还欠着的

- **没有告警**：出了问题没人通知
- **没有异地备份**：板子挂了数据就没了
- **串流受网络限制**：CGNAT 导致周期性卡顿
- **NPU 完全闲置**：6 TOPS 算力一次没用
- **没有 CI/CD**：改代码还是要手动构建

### 不想做的

- 媒体服务器（宿舍没硬盘位）
- 智能家居（不能改宿舍电路）
- 摄像头安防（不合适）
- 更多自建服务（装了也是吃灰）

## 最后

这块板子的价值不在于"跑了多少服务"，而在于：

**把日常重复的事情自动化掉，把分散的东西统一起来，并且随时知道它还好不好。**

它不完美——串流会卡、NPU 空着、没有告警。但该干的事都干了，而且干得还算稳。

如果有天它挂了，我知道怎么从零重建；如果哪天想加东西，也有清晰的扩展路径。

这就够了。
